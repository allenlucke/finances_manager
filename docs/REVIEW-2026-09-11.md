## P. Parsers and the AI service

**P1. A same-date running-balance export stores the wrong opening and closing balance, permanently.**
*[reproduced]* `csv_reader.py:429` decided file order by comparing the first and last dates, so a
one-day newest-first file was read backwards: closing came back as the oldest balance and opening as
the same figure, no warning. A statement is unique per `(account, period_end)` and nothing deletes
one, so a corrected re-import cannot replace it.
*Closed in batch 1:* order is inferred from the balance chain itself — each known balance implies a
balance-before-everything under either ordering, and the ordering under which every known balance
agrees is the file's. Dates break a tie; when neither resolves it the file is flagged and no
checkpoint balance is recorded. A blank or unreadable balance on any row, including the newest or
oldest, is walked through by movement rather than guessed around.

**P2. A multi-statement OFX files every account's rows into the nominated one.** *[verified]*
`ofx_reader.py:72-91` emitted no account key, took the summary from the first statement, and its own
warning about this was dropped by J1. Two accounts in one file with the same FITID became one row and
one "duplicate".
*Closed in batch 1:* each statement's `ACCTID` becomes the row's `account_mask`/`account_key`, so the
API routes rows through the unlinked-account flow exactly as it does for a brokerage history; a
multi-statement file records no checkpoint and says so. A single-statement file is unchanged.

**P3. The `generic` format assumes negative means money out.** *[plausible]* Any file with
`Date, Description, Amount` matches it. American Express writes charges positive and payments
negative, so every purchase would import as a credit with no warning and no checkpoint to catch it.
*Closed in batch 1:* an `amex_card` format registered ahead of `generic` with the sign convention
inverted, and `generic` warns when most rows are positive.

**P4. A negative figure in the credit column was read as a positive credit.** *[reproduced]*
`csv_reader.py:585` took `abs()` of the credit column while respecting the debit column's sign.
*Closed in batch 1.*

**P5. The rule-table test runs on text the rules never see.** *[reproduced]*
`test_rules_table.py:51` uppercases the example; production normalizes the merchant first, which
strips trailing store numbers, so the `QT 1234` and `BP#9876` examples cannot match end to end.
*Closed in batch 1:* the table test builds its transaction the way the CSV reader does, and the two
rules were rewritten to match what reaches them.

**P6. An OFX parse failure echoed the library's exception text.** *[verified]* `ofx_reader.py:63`
put `str(exc)` in the 422 detail, which can quote the file. With J1 passing details through, the
message is now the exception class alone.
*Closed in batch 1.*

**P7. `account_key` is reversible.** *[reproduced]* `common.py:54` is a truncated, unsalted SHA-256
of the account number, stored as `account.external_id` beside the mask, returned to the browser, and
relayed into Claude's context by the MCP tools. A ten-digit number was recovered from key plus mask
in 0.22 seconds. *Batch 2.*

**P8. `\bTRANSFER\s+(TO|FROM)\b` flags payments to people as transfers.** *[reproduced]*
`rules.py:143`: "ZELLE TRANSFER TO PLUMBER JOE" and "WIRE TRANSFER TO ACME CONTRACTORS" are marked
transfers, which the CHECK constraint makes uncategorizable, and the API has no un-mark operation.
Latent until M3 calls `/categorize`. *Batch 4.*

**P9. Smaller.** The positions reader's row loop is outside its `csv.Error` guard
(`positions_reader.py:85`). The money parser strips interior spaces, so `84 31` reads as 8431
(`common.py:89`). `models.py:46` still says the parser's `dedupe_key` is used by the API. `raw` ships
every column on every row, unread by Java, behind a blocklist rather than an allowlist. *Batch 4.*
